# STRUCHORD — ROADMAP (план будущего)

Заведён 2026-08-25 по решениям ask_user:
- формат: **отдельный ROADMAP.md** (README.md остаётся журналом прошлого — только растёт вглубь; этот файл — план, живёт и переписывается);
- приоритеты: предложил ассистент (оценка «размер × польза × риск»), **ждут утверждения пользователя одной правкой**;
- ритм: **поток + фиксация** — идеи приходят на ходу, но каждая сразу встаёт строкой в Backlog, и волна стартует только оттуда.

## Правила

- **R1.** README = прошлое (спеки, прогоны, sha). ROADMAP = будущее (очередь, статусы, реестр). Ничего не дублируем, ссылаемся.
- **R2.** Любая новая идея — сначала строка в Backlog (статус «новая»), потом волна. Волна на старте получает «в работе», на сдаче — «сдано» + sha.
- **R3.** Один фронт: одновременно в работе ровно одна волна.
- **R4.** Отменённое не стираем: статус «отменено» + причина (история решений дороже чистоты списка).
- **R5.** Чистки — отдельные волны, не вперемешку с фичами.
- **R6.** Каждая сдача ритм-линии: обновить реестр (sha/sw) + запись в README (как делаем).
- **R7.** При изменении `STRUCHORD.html` держать видимую версию приложения в шапке (`STRUCHORD · ver 0.xx`) актуальной вместе с `sw.js` / `CACHE_NAME`, чтобы пользователь сразу видел текущий build.

## Рабочий формат с пользователем

Зафиксировано 2026-08-31 по B-31: пользователю нравится формат совместной итерации «обсудили ощущение → узкий прототип → проверка в живом браузере → точечная доработка». Если сессию продолжает другой агент, держать этот формат.

- Говорить по-русски, кратко, но технически точно. Не прятать сомнения: если поведение визуальное — лучше дать проверить в preview, чем обещать на словах.
- Перед реализацией спорной анимации сначала уточнять желаемое **ощущение/картинку**, а не только технический механизм. В B-31 ошибка была в слишком буквальном «overlay/guide» вместо нужного smooth snapped resize.
- Работать малыми шагами: один видимый сценарий за раз. Для B-31 сначала граница между ячейками; правый край квадрата — только после визуальной приёмки принципа.
- Для анимаций держать критерий пользователя: «дорого», плавно, без дёрганья и без ощущения дешёвой заглушки. Если пользователь говорит «было лучше» или «отменяй» — быстро откатить/зафиксировать причину, не защищать неудачный вариант.
- Производительность не опускать: цель 60fps. На `pointermove` избегать полного `render()`, `innerHTML`, тяжёлого reslice/settle и записи модели; допустима только локальная дешёвая геометрия с rAF/throttle.
- Сдача визуальной фичи — только после ручной проверки пользователем в live preview. Тесты обязательны для регрессий, но не заменяют визуальную приёмку.
- **Скриншоты/shot-tools не запускать без необходимости.** Использовать их только если пользователь попросил или визуальный баг нельзя понять иначе; по возможности сначала обсудить, что именно снимаем.

### B-31: диагноз «серого пятна» правого края и фикс (2026-09-01, ver 0.99)

### Tooltip аппликатуры при pinch-зуме (2026-09-02, ver 0.113)

Заметка пользователя: «когда наводишь мышь на ячейку с аккордом, тултип аппликатуры появляется ровно где нужно; но стоит увеличить страницу жестом двумя пальцами — тултип появляется вообще не там, как будто в рандомном месте».

Диагноз (CDP Emulation.setPageScaleFactor = pinch): при visual-viewport зуме `window.innerWidth/innerHeight` остаются layout-размерами (у меня 1200x800 при видимом 750x500), а тултип с `position:fixed` позиционируется/clампится по ним. Плюс на реальных жестах clientX/Y приходят в visual-px, а кэш rects — layout-px.

Фикс 0.113:
- `tooltipViewportMetrics()`: видимый регион в layout-px через visualViewport (offset/scale, size/scale); при scale===1 вырождается в прежние innerW/H — поведение бит-в-бит;
- `positionMainTooltip`/`positionPreviewTooltip`: свободное место, fitsVertically, fallback-центр и все прижатия — от видимого региона;
- `mouseEventToLayoutXY(e)`: нормализация clientX/Y в layout-пространство для хиттеста вооружения кнопок (при scale===1 — тождественно).

Проверено: scale 1.0 — без регрессий (якорь dx=21 dy=-4, тултип в регионе), синтетический pinch в headless ограничен (CDP-события идут в layout-px, :hover при синтетике ненадёжен) — финальная приёмка на реальном жесте у пользователя.
