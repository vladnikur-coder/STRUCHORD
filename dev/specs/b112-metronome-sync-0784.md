|---|---|
| что слышно | `early` — pad опережает щелчок |

## Замер «до» (read-only, код не менялся)

Диагностический скрипт `/tmp/pad-metronome-audit.js` (в репозиторий не вошёл) вытащил из HTML реальные `parseTimeSig`, `getGridUnitDurationSeconds`, `getEventDurationForTimeSig`, `getSquareEventOffsetSeconds` и свел границы pad с сеткой кликов из `scheduleMetronomeEvents`.

| ситуация | граница pad против щелчка | заход слайда |
|---|---|---|
| 4/4 @120, четыре такта | **0 мс** — совпадает идеально | 0,35 с = **18 % ячейки**, начинается за ⅔ доли до щелчка |
| A @120 → B @140 | **214,3 мс** на первом же такте B, дальше скачет | 0,343 с |
| смешанный размер 4/4 → 2/4 → 4/4 | 0 мс | 0,20–0,35 с |
| 6/8 @120 | 0 мс | 0,30 с |
| 4/4 @180 | 0 мс | 0,267 с = 20 % ячейки |
| короткая ячейка span=1 | 0 мс | 0,10 с |
| метроном на восьмые, 4/4 @120 | 0 мс, но **щелчок 1,75 с попадает внутрь окна 1,65–2,00 с** | 0,35 с |

Ключевой вывод: **часы в обычной песне и так совпадали**. То, что владелец слышит как «pad опережает», — не дрейф, а сам ранний заход, принятый в 0.782 по видео. В эталоне `uploads/Follow for daily chord progressions!.mp4` аккорд длился ≈3,8 с и 0,35 с были ≈9 % такта; в приложении ячейка чаще 2 с, и та же величина стала ≈18 % — вдвое заметнее на фоне метронома.

Вторая, **независимая** поломка: `scheduleNextEvent()` перевешивал сетку щелчков только по `tsChanged` (смена размера). Смена BPM секции проходила мимо — pad шёл по новому темпу, метроном продолжал по старому. `reanchorMetronomeForTempo()` при смене темпа на ходу вешал новые часы на якорь, посчитанный под **старый** BPM. А включение метронома или смена доли на ходу вызывали `scheduleMetronomeEvents()` без `resumeAtNow`: все прошедшие клики планировались в прошлом и звучали разом («залп», 7 кликов на 3-й секунде при 120 BPM).

## Что сделано

### 1. Заход слайда от доли метронома — `keyboard-accompaniment.js`

Вместо «всегда 0,35 с» рабочая длина считается как **⅓ пульса метронома**:

```
lead = max(0,05; min(⅓ · pulse; 0,35 с; 20 % ячейки))
pulse = 60/BPM, а в составном размере (6/8, 9/8, 12/8) — 1,5 · 60/BPM
```

| BPM | было | стало |
|---|---|---|
| 120 (4/4) | 0,350 с | **0,1667 с** |
| 180 (4/4) | 0,267 с | **0,1111 с** |
| 60 (4/4) | 0,350 с | **0,3333 с** |
| 40 (4/4) | 0,350 с | 0,350 с (предел из видео) |
| 120 (6/8) | 0,300 с | **0,250 с** |
| ячейка 0,5 с | 0,100 с | 0,100 с (ограничение 20 %) |

`PAD_GLIDE_LEAD = 0,35` сохранён как **верхний предел** и как ответ `padGlideLead()` без аргумента (превью, экспорт, старые вызовы). Добавлены `padGlideLeadFor(o)` и `padPulseSeconds(o)`; `padFigure()` берёт `lead` из них. Нет `o.bpm` (превью/экспорт) — запасные 120 ударов. Smoothstep по `playbackRate`, 33 точки, предел 7 полутонов, `hold` общих тонов, перетекание между секциями, мягкое гашение пустой ячейки/паузы/конца песни — **не изменились**. `keyboard-audio.js` не правился по существу (только комментарий): его ограничение `min(lead, dur·0,45)` продолжает работать.

### 2. Метроном живёт на тех же часах, что и pad — `STRUCHORD.html`

- Введён `metronomeGridKey`: `[размер, BPM, доля метронома, точка запуска]`. Якорь квадрата **намеренно не входит** в ключ — он пересчитывается на каждом событии и дрожит на последних знаках; иначе планировщик перезапускался бы перед каждой ячейкой и акценты плясали.
- `stopMetronomeScheduler()` сбрасывает ключ: Стоп, пауза, выключение метронома, смена доли, восстановление аудиоконтекста и перемотка автоматически требуют нового перевеса.
- `scheduleMetronomeEvents()` запоминает ключ своих часов.
- В `scheduleNextEvent()` сетка перевешивается, когда ключ изменился: **смена BPM секции, смена размера, смена доли, новый запуск** — от свежего `playbackState.squareAnchorTime`, с `resumeAtNow=true`. Якорь фазы такта 0.783 (`evStart − getSquareEventOffsetSeconds(...)`) не тронут.
- `reanchorMetronomeForTempo()` больше не вешает новые часы на старый якорь: он лишь помечает ключ недействительным, и новый темп вступает **со следующего аккорда** — ровно как обещает подсказка `applyBpmChange()` («BPM N: новый темп со следующего аккорда»).
- `toggleMetronome()` и `setSubdivision()` при работе на ходу получили `resumeAtNow=true`: включение метронома больше не выдаёт залп запоздалых щелчков.

## Замер «после» — `dev/tests/b39-metronome-sync-0784.js`

Тест вытаскивает **реальные** функции из HTML в `vm`-песочницу с управляемыми часами Web Audio и mock'ом `requestAnimationFrame`, эмулирует пропатченный блок `scheduleNextEvent` и прогоняет кадры по 10 мс.

| сценарий | до | после |
|---|---|---|
| ровный 4/4 @120, 4 такта | 0 мс | **0 мс** |
| заход на восьмых (subdivision=2) | лишний щелчок внутри окна 0,35 с | **0 щелчков** внутри окна ⅓ доли |
| A @120 → B @140 | **214,3 мс** | **0 мс** |
| 6/8 @120 | 0 мс | **0 мс**, заход 0,25 с |
| смена темпа на ходу | залп + уезд | **0 мс**, залпа нет |
| включение метронома на 3-й секунде | **7 кликов залпом** | **1 клик по сетке**, ни одного в прошлом |

10 групп: статический контракт (версия/кэш парой, ключ часов, `resumeAtNow`, 0.783 цел), `padGlideLeadFor` (BPM, 6/8, предел, короткая ячейка, превью), `plan()[0].pad.lead`, ровный темп, восьмые, смена BPM секции, 6/8, смена темпа на ходу, включение на ходу, устойчивость ключа.
