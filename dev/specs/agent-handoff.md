## B-123 · 0.824: Safari Web Audio requires playback Audio Session

- Владелец: Safari 17.6 / macOS, HTMLAudio слышно, Web Audio — нет. Его отчёт:
  контекст `running`, `resume-resolved`, тестовый осциллятор `scheduled` → `ended`,
  ошибок нет; `navigator.audioSession.type` всюду `auto`. Пересоздание контекста
  (generation 2/3) тоже не помогло.
- Для Safari Web Audio-only документа одной `AudioContext.state === 'running'`
  недостаточно для активации playback media session. На явном пользовательском
  audio-preflight выставлять `navigator.audioSession.type = 'playback'`, затем
  повторно выставлять при managed resume и rebuild. Feature detect; без API — no-op.
- Тест `dev/tests/b123-safari-audio-session-0824.js` имитирует API в Chromium:
  gesture → playback, reset → resume reassert, reset → context rebuild reassert.
  **Не считать Safari починенным до того, как владелец подтвердит слухом после патча.**
- Спека/отчёт: пока не созданы; сначала дождаться результата Safari.

## B-122 · 0.823: запись и песня на одних часах

- **Дубли функции побеждают молча.** В патч добавлялись новые `driftPlaybackRate()` и
  `scheduleAudio()`, а старые однострочные объявления тех же имён оставались ниже в
  файле. Объявления функций поднимаются (hoisting), последнее выигрывает: приложение
  выглядело пропатченным, а работал старый код, и тест «падал непонятно». Любой патч,
  который **переопределяет** функцию, обязан удалить старую строку объявления
  (в патче — отдельные `replace(..., '')` перед вставкой).
- **jsdom 20:** у `Blob` нет `arrayBuffer()`. Тестам нужен свой `Blob`-мок или обход.
- **Песня без байтов в хранилище** даёт `getPathInfo().path === 'none'`
  (`mainTrackAllowed() === false`). Сначала `bt.importEmbedded({backingTrack:{…, embedded: base64}})`,
  потом `bt.loadSong({backingTrack: meta})`.
- **Ползунок скорости в тесте.** Ветка перезапуска в `#btSpeed.oninput` работает только
  при `playbackState.isPlaying === true`; при ручном `preparePlaybackStart()` флаг нужно
  поставить самому, иначе проверка молча идёт по другой ветке.
- **Буфер из временного `AudioContext`** (так строятся пики волны) рабочий контекст
  принимает — проверено в реальном Chromium 149
  (`dev/tests/b122-audio-sync-browser-0823.js`). Опыт полезен и вне B-122.
- **Кадры в puppeteer:** `page.setViewport({isMobile:true})` перезагружает документ
  (со `waitUntil` можно получить таймаут). Надёжнее — новая страница под каждый размер.
  `await` внутри `page.evaluate` с длинной цепочкой промисов ловит
  `Promise was collected`; запускать работу «выстрелил и забыл» и ждать флаг из Node.
- **Кадры панели волны** могут уйти ниже сгиба (ландшафт телефона) — перед снимком
  `scrollIntoView({block:'center'})`, иначе на кадре нет предмета проверки.
- **Отчёт и правила:** спека `dev/specs/b122-audio-sync-0823.md`,
  отчёт `dev/bench/results/b122-audio-0.823/REPORT.md`.

## B-39 · MIDI-derived groove profiles 0.801

R8 confirmed before code: compact descriptors only (no source note sequences in app), subtle section development, automated all-folder/all-supported-meter checks, no new UI. `STRUCHORD.html` embeds aggregate profile vectors for 9 app genres × 3 supported meters × 8 roles; they were derived from 23,707 MIDI files across all 109 source folders. Profiles contain velocity-weighted attack phases, relative density, velocity delta, and a bounded mean-pitch register proxy. Genre routing is a weak name-based prior; attack-phase vectors rank authored groove candidates (phase 0.62, density 0.23, family prior 0.15). Role density is blended at 45% of a ±10% cap; velocity delta at 45% of ±4; register can bias only the choice among existing single-note chord tones by at most one index. Legacy calls without integer `phraseSeed` do not use profiles. Manual cells and saved patterns on load are not rewritten. 578 MIDI files in unsupported meters are outside this prototype; the corpus has no dedicated punk folder, so punk uses nearby high-energy source categories. Tests: `b39-corpus-groove-profiles-0801.js`, `b39-auto-cohesion-0800.js`, `b39-performance-prototype.js`, HTML syntax. Browser suites requiring Puppeteer cannot run in this environment. No subjective audition/A-B yet. Rebuild: `analyze_ezkeys_corpus.py` → `build-b39-corpus-groove-profiles.py` → patcher. Spec: `dev/specs/b39-corpus-groove-profiles-0801.md`.

## B-104 · тембр — это исполнение 0.776

Один HTML больше не обязателен (прямое решение владельца). Звук клавишных и клавишный аккомпанемент вынесены в `keyboard-audio.js` и `keyboard-accompaniment.js`. Оба файла — фабрики в `window.__b39Modules[name]`, HTML вызывает `b39BootModule('audio')` ровно там, где раньше лежал код. **Не выносить блоки через `<script src>` напрямую:** inline-код исполняется до внешних файлов, и обращение к `__b39Modules.audio()` падает с `Cannot read properties of undefined`. Новый тест или правка, тянущие модуль, обязаны идти через `b39BootModule`.

Записанные звуки теперь `sounds/` (манифест + mp3), а не 10,7 МБ base64 в `keyboard-sounds.js`. Сборщик `dev/tools/build-keyboard-sounds.py` больше не нуждается в старом файле: если его нет, он качает те же записи из их репозиториев (Salamander через npm, Rhodes/орган/pad через GitHub API). Rhodes лежит **WAV** — у него записанная петля по сэмплам, mp3 добавил бы задержку кодера и щелчок на стыке; манифест и `write_sample` выводят расширение из самого файла, не подменять обратно на `.mp3`.

Грабли:
- Без `await StruChordSampleBank.load(mode, ctx)` банк пуст и `scheduleEvent`/`playNote` молчат — в браузерных тестах загрузка банка идёт до замера.
- `previewNote` планирует ноту на `currentTime + .02`: при `.01` первый удар с сэмплами иногда попадал в прошлое и Web Audio молча играл его сразу, тест «звук запланирован сразу» падал через раз.
- `b39-sound-cache-0771` требует `page.reload()` после `navigator.serviceWorker.ready`: первая загрузка только ставит SW, страницу он обслуживает со второй.
- Офлайн-рендер яркости: одна свежая страница на тембр (`OfflineAudioContext` после реального контекста даёт `InvalidAccessError`), метрика — DFT-отношение 8-й гармоники к основному тону, полоса highpass тут непригодна.
- Прежние тесты 0.769/0.771 переписаны под новую структуру, но смысл сохранён: в HTML нет ни одного образца, лицензии в настройках, манифест указывает на существующие файлы.

## 2. Тесты: где легко ошибиться

- **Проверка может держаться за то, что уже удалено.** `b12-tab-techniques-browser.js`
  искал атрибут `data-tab-tech-mark`, а он исчез ещё в 0.692 вместе с самодельной
  отрисовкой мини-таба (его рисует alphaTab). На `origin/main` набор был зелёный,
  потому что там старая сборка. Вывод: сначала `git log -S"<имя атрибута>"`,
  потом решать — тест устарел или поведение потеряно. Молча вычёркивать проверку нельзя.
- **alphaTab рисует кадр не мгновенно.** После «Применить» проверять картинку сразу
  бессмысленно: нужно ждать `[data-tab-thumb][data-thumb-done] svg`.
- **Служебный `<svg>` для `<defs>` не должен иметь числовых `width`/`height`.**
  Аудит B-79 считает `width="0" height="0"` немасштабируемым размером
  (`svg-size = 1` при допустимом 0). Размеры держим в CSS (`width:0;height:0`),
  числовые атрибуты не возвращаем. На 0.679 аудит проходил — регресс появился позже.
- **Шапка главного экрана на 320 px** — давнее падение `b13-home-screen.js`
  (шапка занимала 367 px). Лечится `flex-wrap: wrap; row-gap` у `.home-header`
  и `margin-left: auto` у `.home-header-controls`. Не убирать — вернутся 3 FAIL.
- **Мобильная главная и инлайн-элементы.** Любая вставка в строку названия ломает
  390 px: появлялась горизонтальная прокрутка 54 px. Нужна обёртка-колонка
  (`.home-brand-text`), а не инлайн-текст рядом с логотипом.
- **Цвет и контраст.** `--color-text-tertiary` не проходит WCAG AA (3,22:1).
  Мелкие подписи — `--color-text-secondary` (8,68:1). Проверять замером, не на глаз.

## 6. Git и PR

- Пуш только в ветку текущей сессии `arena/…`, без force-push (R9).
- Перед PR: `git fetch` → `git rev-list --count origin/main..HEAD` → `git merge-tree
  --write-tree` на конфликты. Мусор вроде `*.bak`, `*.log`, архивов из `uploads/`
  в ветке не должен попадать в PR.
- Перегенерированные кадры тестов после прогона корпуса показываются как изменённые
  PNG. Это не правка продукта: смотреть на них глазами не нужно, перед коммитом
  такие файлы откатывать (`git checkout -- dev/bench/results`), а не тащить в историю.
